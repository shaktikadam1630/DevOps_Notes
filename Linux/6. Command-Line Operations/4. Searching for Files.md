# Searching for Files

This module covers standard I/O streams, redirection, pipes, wildcards, and the two core search tools every Linux user relies on: `locate` and `find`.

---

## 1. Standard File Streams

Every command has **three standard file streams** open by default:

| Name | Abbreviation | File Descriptor | Default Source/Destination |
|---|---|---|---|
| Standard input | stdin | 0 | Keyboard |
| Standard output | stdout | 1 | Terminal |
| Standard error | stderr | 2 | Terminal |

By default, stdin comes from your keyboard, while stdout and stderr both print to your terminal. Each can be **redirected** elsewhere:
- **stdin** can come from a file or a previous command's output (pipe)
- **stdout** is often redirected into a file to save results
- **stderr** is often redirected to a separate error-log file to keep errors out of normal output

> A successfully-running command typically writes **nothing** to stderr — it's reserved for errors and warnings.

All open files are tracked internally as **file descriptors** — numbers starting at 0. Any files a command opens beyond the standard three get the next available number, starting at 3.

## 2. I/O Redirection

![Standard Streams & Redirection](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/streams-redirection.png?raw=true)

**Redirect input** from a file using `<`:
```bash
do_something < input-file
```

**Redirect output** to a file using `>`:
```bash
do_something > output-file
```

**Both at once:**
```bash
do_something < input-file > output-file
```
Note: stderr is separate — error messages still print to the terminal here, since only stdout was redirected.

**Redirect stderr specifically**, using its file descriptor number (`2`):
```bash
do_something 2> error-file
```

> `do_something 1> output-file` is identical to `do_something > output-file` — the shell assumes descriptor `1` when none is specified.

**Combine stdout and stderr into one file** using `2>&1` ("send fd 2 to wherever fd 1 is currently going"):
```bash
do_something > all-output-file 2>&1
```

**Order matters** — `>` sets stdout's destination first, then `2>&1` points stderr at that same place. Writing it reversed (`2>&1 > all-output-file`) does **not** combine them, since redirections are read left to right.

**Shorter bash-specific form:**
```bash
do_something >& all-output-file
```

**Example:** Running a backup script overnight with `backup.sh > backup.log 2>&1` captures everything — successes and failures alike — in one file you can review the next morning, instead of errors scrolling past unseen on an unattended terminal.

## 3. Pipes

The Unix/Linux philosophy: many small, simple commands working together, rather than one large program with every feature built in. **Pipes** make this possible — connecting one command's stdout directly to the next command's stdin.

```bash
command1 | command2 | command3
```

This is a **pipeline**. Example:
```bash
ls | wc -l
```
`ls` lists files; its output feeds into `wc -l`, which counts lines — giving you a file count with no intermediate file needed.

**Why pipelines are efficient:**
- **Commands run concurrently** — each starts processing data as it arrives rather than waiting for the previous command to fully finish, making good use of multi-core systems
- **No temporary files needed** — data flows directly between commands, saving disk space and avoiding slow disk I/O

**Example:** `dmesg | grep error` filters kernel log output for the word "error" in one step — no need to save the full log to a file first, then search it separately.

## 4. Searching for Files: Overview

Two primary tools: **`locate`** and **`find`**. You can also use **wildcards** in Bash to match file patterns without naming each file explicitly.

---

## 5. The locate Utility

`locate` searches a **prebuilt database** of files/directories, matching entries containing a specified text string. Because it searches a database rather than scanning the disk live, it's **very fast** — but can return long lists.

**Narrowing results with `grep`:**
```bash
locate zip | grep bin
```
Lists entries containing both `zip` (matched by `locate`) and `bin` (matched by `grep`) — e.g., `/usr/bin/gzip`. These strings can match anywhere in the full path.

**The database:** built by `updatedb`, usually rebuilt automatically on a schedule (often daily). A very recently created file may not show up in `locate` results until the next update. Update manually:
```bash
sudo updatedb
```

> **Note:** `locate` isn't always installed by default. Modern distros often ship **`plocate`** — a faster drop-in replacement for the older `mlocate`. Both provide the same `locate`/`updatedb` commands.

**Example:** Searching `locate .conf | grep nginx` instantly surfaces every nginx-related config file path system-wide — far faster than manually browsing `/etc` looking for them.

## 6. Wildcards and Matching Filenames

Wildcards are a **shell feature** — the shell expands the pattern into matching filenames *before* the command even runs. This is why wildcards work with virtually any command.

| Wildcard | Matches |
|---|---|
| `?` | Any single character |
| `*` | Any string of characters (including none) |
| `[set]` | Any single character in the set — e.g., `[adf]` matches a, d, or f |
| `[!set]` | Any single character **not** in the set |

**Examples:**
```bash
ls ba?.out          # 3-letter filename starting "ba", ending ".out"
ls *.out             # any filename ending in .out
ls file_[abc].out    # matches file_a.out, file_b.out, file_c.out only
ls file_[!abc].txt   # matches file_X.txt where X is NOT a, b, or c
```

> If a pattern matches nothing, bash passes the literal pattern through unchanged — `ls *.out` with no matches produces an error about a file literally named `*.out`.

### Wildcards with du (disk usage example)

```bash
du -sh a*            # all files starting with "a"
du -sh a*log*        # files starting with "a", containing "log" anywhere
du -sh a[p-z]*       # files starting with "a", second letter p through z
```

### The Globbing Danger

The shell expands wildcards **before** passing them to a command — this is called **globbing**. Sometimes that's not what you want.

**Example of the problem:**
```bash
sudo apt-get install vmware*
```
If files like `vmware-network.log` exist in your current directory, the shell expands `vmware*` into all matching **filenames** first — passing garbage (log filenames, not package names) to `apt-get`, causing errors.

**The fix — quote the argument** to prevent shell expansion, letting the command interpret the wildcard itself:
```bash
sudo apt-get install "vmware*"
```
Now `apt-get` receives the literal string `vmware*` and expands it against its **own** package list instead.

**Example:** This exact mistake — an unquoted wildcard accidentally matching local files instead of the intended package names — is one of the most common "why did this command do something weird" moments for people new to the shell.

## 7. The find Utility

`find` **recurses** down the filesystem tree from a starting directory (default: current directory), locating files matching specified conditions.

**Common real-world uses:** scanning for large old core dump files to clean up, clearing stale files from `/tmp` or `/var/cache/` — often automated via `cron`.

### Basic Usage

With just a starting directory, `find` lists everything in it and its subdirectories. Narrow results with:

| Option | Purpose |
|---|---|
| `-name` | Match files by name pattern |
| `-iname` | Same as `-name`, case-insensitive |
| `-type` | Restrict to a type: `d` (directory), `l` (symlink), `f` (regular file) |

```bash
find /usr -name gcc            # files/dirs named "gcc"
find /usr -type d -name gcc    # only directories named "gcc"
find /usr -type f -name gcc    # only regular files named "gcc"
```

### Limiting Depth

```bash
find . -type d -maxdepth 1
```
Restricts how many directory levels deep `find` descends — useful for avoiding an overwhelming list of nested subdirectories.

### Running Commands on Results: -exec

```bash
find -name "*.swp" -exec rm {} ';'
```
`{}` is a placeholder replaced by each matching filename; the command runs once per match. End with `';'` (with straight quotes) or `\;`.

> **Important:** Use straight single quotes (`'`), not "smart" quotes — copying from a formatted document can break this.

**Safer alternative — preview before acting:**
```bash
find -name "*.swp" -ok rm {} ';'
```
`-ok` works like `-exec` but **prompts for confirmation** before each execution.

**Combining with grep:**
```bash
find . -type f -exec grep -H "log" {} \;
```

**Shortcut for detailed listing** (equivalent to piping into `ls -l`, but with more detail like inode numbers):
```bash
find . -type f -ls
```

### Finding by Time

```bash
find / -ctime 3
```
`-ctime` = when the file's **inode metadata** (ownership, permissions) last changed — **not** creation time (standard `find` doesn't track creation time at all). Also available: `-atime` (last accessed), `-mtime` (last modified). Minute-level equivalents: `-cmin`, `-amin`, `-mmin`.

**Time value syntax:**
| Syntax | Meaning |
|---|---|
| `n` | Exactly n days |
| `+n` | More than n days |
| `-n` | Fewer than n days |

### Finding by Size

```bash
find / -size 0
```
Default unit: 512-byte blocks. Other units: `c` (bytes), `k` (KB), `M` (MB), `G` (GB) — same `n`/`+n`/`-n` syntax applies.

```bash
find / -size +10M -exec command {} ';'
```

### Finding Files Newer Than a Reference File

```bash
find . -newer /var/log/btmp
```
Finds everything modified more recently than the reference file's timestamp.

> **Tip:** Searching from `/` as a regular user often produces many "Permission denied" messages. Practice from a smaller directory (home directory or `/tmp`) for cleaner results, or use `sudo`, or redirect stderr: `find / ... 2> /dev/null`.

**Example:** A sysadmin cleaning up a server runs `find /tmp -type f -mtime +30 -exec rm {} ';'` to delete anything in `/tmp` untouched for over 30 days — a common automated housekeeping task that keeps temporary storage from filling up indefinitely.
