# The Boot Process

This module covers what actually happens between pressing the power button on a Linux machine and seeing a login prompt. It's one of the more technical topics in this series, but even a high-level understanding pays off the first time something goes wrong at startup.

**Note:** Some parts of the boot process get quite technical — you don't need to master every detail right away to use Linux effectively. Come back to this section later, once you're more comfortable navigating the system, to deepen your understanding.

This module focuses on the **x86 architecture**, which powers most desktop and laptop computers, since that's what you're most likely to be working with.

---

## 1. Introducing the Boot Process

The **Linux boot process** is the sequence of steps that occurs from the moment a computer is powered on until the operating system is fully loaded and ready for use.

Knowing this process is genuinely useful, not just theoretical — it helps with:
- **Troubleshooting startup issues** — a specific error message usually points to a specific stage that failed
- **Improving system performance** — understanding what loads and when
- **Customizing how your system loads** — for advanced configuration down the line

![The Linux Boot Process](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/linux-boot-process.png?raw=true)

**Example:** If your screen shows "No bootable device," you instantly know the problem is in the very first stage — before Linux even starts loading. That's the power of knowing this sequence: a scary black screen becomes a specific, solvable problem.

---

## 2. BIOS — The First Step

When you power on the computer, the **BIOS (Basic Input/Output System)** begins the startup process.

BIOS is a small program stored on a **read-only memory (ROM) chip** on the motherboard. It's the very first software that runs when you power on your computer — even before the operating system is involved.

### What BIOS Actually Does

The BIOS performs a series of checks called the **Power-On Self-Test (POST)**. During POST, it initializes critical hardware components — screen, keyboard, memory — making sure everything works correctly before the operating system loads. The BIOS then finds and loads the **bootloader**, which starts the operating system.

**Example:** If you've ever heard your computer beep in a specific pattern right after powering on with nothing on screen, that's POST detecting a hardware failure (like missing RAM) before it can even hand off to the bootloader.

**In short:** BIOS acts as a bridge between your computer's hardware and its operating system, making sure everything is ready before the OS takes over.

---

## 3. Master Boot Record (MBR), EFI Partition, and Boot Loader

Once POST is complete, control passes from the BIOS to the **boot loader** — a small program stored on one of the system's storage devices.

- On traditional **BIOS/MBR** systems, the boot loader lives in the **boot sector** of the disk.
- On modern systems using **UEFI** (Unified Extensible Firmware Interface), it's stored in the **EFI partition** instead.

Up to this point, the computer hasn't yet accessed its mass storage devices. The system also retrieves the current date, time, and hardware configuration from the **CMOS** — a small battery-powered memory chip that retains data even when the system is powered off.

![BIOS Boot vs. UEFI Boot](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/bios-vs-uefi.png?raw=true)

### Common Boot Loaders

| Boot Loader | Used For |
|---|---|
| **GRUB** (GRand Unified Boot Loader) | The most common boot loader for Linux distributions |
| **ISOLINUX** | Booting from removable media (CDs, USB drives) |
| **DAS U-Boot** | Embedded systems and appliances |

Most Linux boot loaders show a menu letting you choose between multiple operating systems or different kernel versions. Once you select an option, the boot loader's main job is to load the **kernel image** and the **initial RAM disk (initrd/initramfs)** into memory — these contain essential drivers and files needed to keep booting until the full OS is loaded.

**Example:** If you dual-boot Windows and Ubuntu, the GRUB menu you see right after turning on your computer — the one asking which OS to load — is exactly this stage in action.

---

## 4. Boot Loader in Action

The boot loader operates in **two main stages**.

### Stage One: BIOS/MBR Systems

The boot loader lives in the first sector of the hard disk — the **Master Boot Record (MBR)**, only **512 bytes** in size, so it can hold only minimal code. During this stage, it:

1. Examines the partition table to locate a bootable partition
2. Loads the second-stage boot loader (like GRUB) into RAM

### Stage One: EFI/UEFI Systems

The process is more advanced. UEFI firmware reads its **Boot Manager** data to determine which UEFI application to launch and where it lives — specifically, which disk and partition contain the **EFI System Partition (ESP)**. The firmware then launches that application (e.g., GRUB) as specified in the boot entry. This is more complex than MBR, but far more flexible and configurable.

### Stage Two: The Second-Stage Boot Loader

This is typically stored under the **`/boot`** directory. At this stage:

1. A splash screen appears, letting you choose which OS and/or kernel version to boot
2. Once selected, the boot loader loads the **kernel** into RAM and passes control to it

Because the kernel is almost always compressed, its first task is to **uncompress itself**. It then checks and analyzes system hardware, initializing built-in device drivers so the OS can continue loading.

**Example:** That brief "GRUB" menu screen with a countdown timer before your OS loads is stage two of the boot loader doing its job — after which control fully passes to the kernel.

---

## 5. Initial RAM Disk

Once the kernel decompresses and finishes its initial hardware probe, it hits a chicken-and-egg problem: it needs to mount the **root filesystem** to access system tools, but the drivers needed to talk to the storage hardware are often stored on that very filesystem. The **Initial RAM Disk (initramfs)** solves this as a temporary bridge.

The initramfs is a small, compressed filesystem image pulled into memory alongside the kernel — a specialized toolkit containing just enough binaries and programs to prepare the system for its final environment.

![The Role of initramfs](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/initramfs-role.png?raw=true)

**What initramfs actually does:**

- **Driver loading via udev** — scans the hardware, identifies mass storage controllers, locates and loads the matching drivers so the kernel can finally "see" the disk
- **Filesystem support** — provides the logic needed to read the filesystem type (ext4, XFS, etc.) used by the root partition
- **Validation and mounting** — locates the root filesystem, performs an error check, and prepares it for final mounting

**Example:** Without a properly built initramfs containing the right drivers, boot would stall completely — the kernel simply can't reach the storage it needs to finish loading. This is exactly why a corrupted initramfs is one of the more common causes of a system that won't boot.

### The Hand-Off: From Temporary RAM to the Real System

Once the hardware is initialized and the root filesystem is verified, the system performs a hand-off in three steps:

1. **Mounting** — the mount program attaches the physical storage to a specific mount point, telling the OS the filesystem is live.
2. **Pivoting** — the system performs a **"switch root,"** pivoting from the temporary initramfs environment to the real root filesystem on disk.
3. **Execution of init** — with the real filesystem established, initramfs is wiped from memory to save space, and control passes to the **init program (`/sbin/init`)** — the "parent of all processes," responsible for starting the rest of the system.

---

## 6. Text-Mode Login

As the boot process nears completion, the `init` process launches several **text-mode login prompts**, letting you enter a username and password to access a command shell. If your system uses a graphical login (GNOME, KDE), these text prompts run in the background and won't be immediately visible.

### Virtual Terminals

Linux handles multiple sessions simultaneously through **virtual terminals**:

| Situation | How to Switch |
|---|---|
| Already in text mode | Press **ALT + Function key** (e.g., ALT+F2) |
| Currently in a GUI | Press **CTRL+ALT + Function key** to reach a text console |
| Returning to the GUI | Press **CTRL+ALT + F1 or F7** (varies by distro) |

Most distributions provide **six text terminals and one graphical terminal**, usually starting from F1 or F2.

**Example:** If your desktop environment ever freezes completely, switching to a virtual terminal with CTRL+ALT+F2 lets you log in via text mode and investigate — even when the graphical side is totally unresponsive.

### The Shell That Greets You

Once you log in through a text terminal, you're typically dropped into a command shell:

- **Default shell:** `bash` (the GNU Bourne Again Shell) is the standard interactive login shell for most Linux distributions.
- **The prompt:** the shell shows a `$` (regular user) or `#` (root) prompt to signal it's ready for input.
- **Execution cycle:** type a command, press Enter, the system executes it, and a new prompt appears — ready for the next instruction.

---

## The Full Picture

Every single Linux boot follows the same underlying story: **BIOS or UEFI** firmware wakes up the hardware and hands off to the **boot loader**, which loads the **kernel** into memory. The kernel leans on a temporary **initramfs** just long enough to mount the real filesystem, then performs a **switch_root** and hands control to **`/sbin/init`** — the parent of every other process on the system. From there, `init` launches the login prompts that eventually put a `$` in front of you, ready for your first command. Understanding this chain is what turns "my computer won't turn on" into "I know exactly which stage is failing."
