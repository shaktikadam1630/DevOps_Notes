# Linux Distribution Installation

This module covers everything involved in actually getting Linux onto a machine: how to pick the right distribution for your situation, how to plan the installation, the different ways installation media and automation work, and two full hands-on walkthroughs — installing CentOS Stream 9 and Ubuntu 24.04 LTS.

---

## 1. Deciding Which Linux Distribution Is Right For You

Before you can install Linux, you need to decide which distribution actually fits your situation. The Linux ecosystem ranges from general-purpose desktop systems to highly specialized server and embedded builds — the options can feel overwhelming, but most decisions come down to a handful of practical questions.

**Note:** Many embedded Linux systems use custom-crafted, purpose-built contents rather than well-known platforms like Android or Yocto.

### Six Questions That Narrow Down the Choice

![Choosing a Linux Distribution](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/linux-distro-decision-factors.png?raw=true)

**1. What is the system's primary role?**
A desktop workstation, a web server, and an embedded device inside a router all have very different requirements — and there are distributions optimized for each.

**Example:** A router manufacturer wouldn't ship a full GNOME desktop environment on a device with 128MB of storage — they'd use a minimal, purpose-built embedded distro instead.

**2. What software does the organization rely on?**
Some distributions are better suited to specific workloads, such as scientific computing, cloud infrastructure, or multimedia production.

**Example:** A research lab running heavy simulation software might lean toward a distro with strong scientific computing package support, rather than a general desktop-focused one.

**3. How much storage is available?**
A full desktop installation can require 20 GB or more, while a minimal server build might fit in under 2 GB. Embedded and IoT deployments may be far more constrained than either.

**Example:** A Raspberry Pi-based IoT sensor with an 8GB SD card needs a distro built to run comfortably in a fraction of that space.

**4. How frequently do packages need to be updated?**
- **Rolling release** distributions (like Arch Linux or openSUSE Tumbleweed) deliver a continuous stream of the latest software.
- **Fixed release** distributions (like Fedora or Ubuntu) batch updates into periodic releases instead.

**Example:** A developer who wants the newest tools the moment they're released might prefer Arch's rolling model; a business running critical infrastructure usually prefers Ubuntu's more predictable, tested release cycle.

**5. How long does a release need to remain supported?**
Many distributions offer **Long-Term Support (LTS)** releases that receive security patches and bug fixes for years — Ubuntu LTS releases, for example, are supported for **five years**. This matters most in production server environments, where stability outweighs having the newest features.

**Example:** A bank running a payment processing server picks an LTS release specifically so it won't need a risky OS upgrade for years.

**6. What hardware will it run on?**
Linux runs across a wide range of processor architectures: **x86-64** (the most common desktop/server architecture), **ARM** (phones, Raspberry Pi, and increasingly servers/laptops), **RISC-V**, and others. Not every distribution supports every architecture.

**Example:** A Raspberry Pi project needs a distro with solid ARM support — not every distribution ships an ARM build at all.

### There's No Single "Correct" Distribution

The best choice always depends on your specific context. Part of building real Linux proficiency is learning to evaluate these trade-offs for yourself rather than looking for one universally "best" distro.

| Question | Key Trade-off |
|---|---|
| Primary role | Desktop vs. server vs. embedded |
| Software needs | General-purpose vs. specialized workloads |
| Storage available | Full install vs. minimal build |
| Update frequency | Rolling release vs. fixed release |
| Support duration | Latest features vs. long-term stability |
| Target hardware | x86-64 vs. ARM vs. RISC-V |

## 2. Planning the Installation

Once you've picked a distribution, the next step is planning three things before you actually install anything: how your disk will be partitioned, what software to include, and how to secure the system from the very first boot.

### Partition Layout

Most distribution installers offer a sensible default layout that works fine for general use. A typical default creates:

- **One large root partition (`/`)** — containing the operating system and most data
- **A smaller swap partition** — used as overflow space when physical RAM is full, roughly equivalent to the Windows pagefile or macOS swap file

For systems with more specific requirements, the installer can be configured to place certain directories on their own separate partitions instead:

- On a **server**, a separate `/var` partition prevents runaway log files from filling the entire disk and crashing the OS.
- On a **multi-user system**, a separate `/home` partition limits how much disk space individual users can consume.

![Partitions on a Linux Hard Disk](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/linux-partition-layout.png?raw=true)

**Example:** A shared university lab server splits `/home` into its own partition — if one student fills their home directory with files, it can't take down the entire system by starving the OS of disk space.

> **Plan before you install!** Partition layout is far easier to define at installation time than to change afterward. Resizing or reorganizing partitions later is possible, but it carries real risk and requires extra steps.

### Software Selection

Every Linux installation includes a minimal base set of packages needed to run the system. From there, most installers let you choose what additional software to add:

| Category | Examples |
|---|---|
| **Graphical interface** | GNOME, KDE Plasma — each with a different look, feel, and workflow |
| **Everyday apps** | Office suites (LibreOffice), browsers (Firefox), media players |
| **Developer tools** | Text editors, compilers, version control tools like Git |
| **Server components** | Apache web server, MySQL database — pre-selectable if the system's role is already known |

**Modern trend:** Most current distributions install a minimal working system first, then let you make these software choices *after* the system is running — reducing the complexity and length of the initial setup.

**Example:** Instead of ticking dozens of boxes during install, a developer installs a minimal Ubuntu Server, boots it, then runs `apt install` afterward to add exactly the packages their project needs.

### Security Setup

Every Linux installation performs some initial security configuration. At a minimum, this involves either:

- Setting a password for the **root (superuser)** account, or
- Configuring a **regular user account with administrative privileges** instead

**Example:** Ubuntu's installer disables direct root login by default and instead creates a regular user who can use `sudo` for admin tasks — a safer default than logging in as root directly.

## 3. Installation Methods

### Installation Media

Like other operating systems, Linux is distributed as an image file — typically in **ISO** format — that you write to a bootable USB drive using a tool such as **Balena Etcher** or **Rufus**. Physical optical media (DVDs) is still technically supported by most distributions but has largely fallen out of use. Once written, the USB drive acts as a self-contained installer: plug it in, boot from it, and the installer starts.

**Network installation:** Most distributions also support booting from a minimal image that downloads the rest of its packages from a server during installation. The protocol that makes this possible is **PXE (Preboot Execution Environment)**, which lets a machine receive a boot image from a server on the local network without needing any local media at all.

**Example:** An IT department provisioning 200 new office laptops uses PXE boot so every machine pulls its OS image directly from a central server — no one has to walk around with a USB drive.

### Automated (Unattended) Installation

Answering the same installer questions by hand across dozens or hundreds of machines is slow and error-prone. Every major distribution family supports **automated installation**, where a preconfigured file answers all the installer's questions in advance.

| Distribution Family | Tool | Format |
|---|---|---|
| Red Hat-based (RHEL, Fedora, Rocky, AlmaLinux) | **Kickstart** | Plain text; auto-generated at the end of a manual install for reuse |
| SUSE-based (openSUSE, SLES) | **AutoYaST** | XML-based |
| Debian-based (pre-Ubuntu 20.04) | **Preseed** | Plain text, using the Debian installer's Q&A system |
| Ubuntu 20.04+ | **Autoinstall** | YAML; replaced Preseed with Ubuntu's newer Subiquity installer |

**Example:** A cloud hosting provider spinning up 500 identical Ubuntu servers overnight uses an Autoinstall YAML file so every server comes up with the exact same configuration, with no one manually clicking through an installer 500 times.

### The General Installation Process

Regardless of which distribution you choose, the broad sequence of installation steps stays consistent — only the visual appearance and specific options differ.

![The Linux Installation Process](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/linux-installation-process-steps.png?raw=true)

1. **Boot from the installation media** — the installer starts instead of an existing OS.
2. **Configuration questions** — language, keyboard layout, timezone, network, partitions, user accounts, software. *(Skipped if an automated install file was provided.)*
3. **Installation** — formats partitions, copies OS files, installs packages, configures the bootloader.
4. **Updates** — optionally download and apply updates during setup.
5. **Reboot and first boot** — the machine restarts into the new system.

### Important: Protecting Your Existing Data

**Installing Linux directly onto a machine will erase all existing data on the target disk.** If you want to run Linux without risking your existing system, there are three safer alternatives:

**Dual Boot** — shrink your existing partition, install Linux alongside your current OS, and choose which to load at startup. Full native performance, but partitioning carries real risk.

**Virtual Machine (Recommended for Learning)** — run Linux inside a window on your current OS using **Oracle VirtualBox** or **VMware**. No changes to your existing partitions; safe and easily reversible.

**Live Boot** — run Linux directly from a USB drive, loaded into memory with nothing written to disk. Zero risk, but nothing persists between sessions.

**Example:** Someone learning Linux for the first time on their only laptop should use a Virtual Machine — it's the only option here where a mistake genuinely can't cost them their existing files.

## 4. Installing CentOS 9 Stream

A hands-on walkthrough installing **CentOS Stream 9** as a virtual machine using **VMware Player**, representing the Red Hat distribution family.

**Step 1 — Create the Virtual Machine:** Open VMware Player, choose **Create a New Virtual Machine**, and point it at your downloaded CentOS Stream 9 `.iso`. Give the VM a clear name.

**Step 2 — Configure Disk and Hardware:** VMware suggests **20 GB** of disk space as a starting point. Bump memory up to **2 GB** and allocate **2 processor cores** if your host machine can spare them.

**Step 3 — Boot Into the Installer:** Select your language, keyboard layout, and time zone. Leave installation source and **automatic partitioning** at their defaults — manual partitioning is a systems administration skill worth learning later.

**Step 4 — Set Root Password and Create a User:** CentOS Stream's installer may leave root disabled and no user created by default — you need to set a strong **root password** and create a standard user account (e.g., `student`) before continuing.

> **Security note:** Using a password that matches the username is fine only for a disposable learning VM — never do this on a real system.

**Step 5 — Finish Partitioning and Begin Installation:** Keep automatic partitioning selected, skip disk encryption for simplicity, then click **Begin Installation**. This typically takes 5–10 minutes.

**Step 6 — Reboot and First Login:** Reboot, log in with your new user account, dismiss or take the welcome tour, and open a terminal to confirm everything works.

**Result:** A working CentOS Stream 9 VM, running the Red Hat family's `dnf` package manager, ready for command-line practice.

## 5. Installing Ubuntu 24.04

A hands-on walkthrough installing **Ubuntu 24.04 LTS** as a virtual machine using **Oracle VirtualBox**, representing the Debian distribution family.

**Step 1 — Create the Virtual Machine:** In VirtualBox, click **New**, give the VM a name without spaces (e.g., `Ubuntu_24.04`), and point it at your downloaded `ubuntu-24.04-desktop-amd64.iso`.

**Step 2 — Configure Hardware:** 2 GB memory and 2 processor cores are reasonable defaults. VirtualBox defaults to a **25 GB** virtual disk (slightly more generous than VMware's CentOS default).

**Step 3 — Boot and Update the Installer:** The VM boots into the "Try or Install Ubuntu" sequence. If prompted, apply an installer update before proceeding for improved reliability.

**Step 4 — Walk Through the Installer:** Choose language, keyboard layout, and network connection. Pick **Interactive Installation** (recommended for first-timers, vs. the automated option meant for repeated deployments). Choose default app selection to keep things simple, and decide whether to install proprietary drivers.

**Step 5 — Disk Setup and Account Creation:** For a VM, choose **Erase disk and install Ubuntu** — this refers only to the *virtual* disk. Create your user account with a strong password, enable password-required login, and set your time zone.

**Step 6 — Review and Install:** Review the summary, click **Install**. This can take anywhere from a few minutes to about 30 minutes depending on host speed. Once done, run `sudo reboot` from a terminal.

**Step 7 — First Boot Setup:** After rebooting and logging in, walk through the short first-boot setup — optionally enable Ubuntu Pro, choose whether to share system data, and skip the app center for now.

**Result:** A working Ubuntu 24.04 LTS VM, running the Debian family's `apt` package manager, ready for command-line practice.

**Example — comparing the two installs:** Both use a VM and ask for a user account and password, but Ubuntu's installer defaults to erasing the (virtual) disk automatically, while CentOS defaults to automatic partitioning with a disabled root account by default — a small but real difference in installer philosophy between the two distro families.

## The Full Picture

Installing Linux comes down to five decisions made in sequence: **which distribution** fits your role, storage, and support needs; **how to partition and secure** the system; **which installation media and method** to use (ISO, PXE, automated, or one of the three safe learning options); and finally, walking through the installer itself — which, as the CentOS and Ubuntu walkthroughs show, follows the same broad five-step process everywhere, even though every distribution family styles it a little differently.
