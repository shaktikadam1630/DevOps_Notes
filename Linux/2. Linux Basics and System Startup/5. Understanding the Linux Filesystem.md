# Understanding the Linux Filesystem

To manage a Linux system effectively, you need to understand how it organizes data. Think of a filesystem like a library: just as a library categorizes books by genre, media type, and frequency of use, a Linux filesystem provides a structured way to store and retrieve data in a human-readable form.

## 1. Common Linux Filesystem Types

Linux is highly versatile and supports a wide array of filesystem formats depending on the hardware and use case.

| Category | Purpose | Examples |
|---|---|---|
| **Conventional Disk Filesystems** | The "workhorses" for standard hard drives and SSDs | **ext4** (most widely used), **XFS** (excellent for large files), **Btrfs** |
| **Flash Storage Filesystems** | Optimized for raw flash memory, like embedded devices | ubifs, yaffs |
| **Special Purpose Filesystems** | Often exist only in memory, providing system information | **procfs** (`/proc`), **tmpfs** (temporary volatile storage) |
| **Database Filesystems** | Treats data as objects/rows in a database rather than simple files, optimized for fast searching, rich metadata, and data integrity | — |

**Example:** A media server storing huge video files performs best on **XFS**. A desktop user who wants one-click rollback after a bad update benefits from **Btrfs** snapshots. A general-purpose server that just needs to be reliable typically runs **ext4**.

## 2. Partitions and Filesystems

When navigating Linux, it's essential to distinguish between **physical storage** (the hardware) and **logical organization** (the software) — the difference between the physical "container" and the logical "method" of storage.

### The Partition — The Physical Container

Imagine your hard drive as a physical office building. A **partition** is a dedicated subsection of that physical media — like a specific floor or suite. In Linux, partitions are identified as device files, such as `/dev/sda1` for the first partition on your primary drive.

### The Filesystem — The Logical Structure

While the partition defines the physical boundaries, the **filesystem** is the logical structure that stores and accesses files within that space. If the partition is the empty office suite, the filesystem is the filing cabinets and indexing system that lets the OS find and retrieve data. Without a filesystem, a partition is just raw ones and zeros. **Formatting** a partition means installing a specific filesystem (ext4, XFS, etc.) onto it.

### Mounting — Bridging the Gap

**Mounting** connects the partition to your usable folder structure. Linux doesn't use drive letters like `C:` or `D:` — instead, you "attach" a partition's filesystem to a specific directory called a **mount point**.

**Example:** You might mount the partition `/dev/sdb1` to the directory `/home`. From that moment on, any file saved in your home folder is physically written to that specific partition — while the rest of the system feels like one seamless tree.

### Windows vs. Linux Storage Concepts

| Feature | Windows | Linux |
|---|---|---|
| Partition Identifier | Disk 1 | `/dev/sda1` |
| Filesystem Type | NTFS / VFAT | ext4 / XFS / Btrfs |
| Mounting Parameters | Drive Letter (e.g., `D:`) | Mount Point (a directory) |
| Base Folder (Root) | `C:\` | `/` |

**Example:** In Windows, plugging in a second drive gives you a new "E: drive" to switch to. In Linux, that same drive just becomes reachable at a folder like `/mnt/data` — no separate "drive" concept, just one unified tree.

## 3. The Filesystem Hierarchy Standard (FHS)

Once everything is mounted into a single unified tree, how does Linux decide where things actually go? That's exactly what the **Filesystem Hierarchy Standard (FHS)** defines.

The FHS is a specification establishing the names, locations, and intended purposes of directories across Linux (and other Unix-like) systems. The current version is **FHS 3.0** (originally released in 2015), now maintained by **FreeDesktop.org** after adopting the standard from the Linux Foundation in November 2025. Most major distributions — Fedora, Debian, Ubuntu, RHEL — follow it closely.

**The core benefit:** it lets you move between Linux systems without re-learning where things are. Configuration files live in the same predictable location on any distribution.

### Key Top-Level Directories

| Directory | Purpose | Windows/macOS Equivalent |
|---|---|---|
| `/` | Root of the entire filesystem tree | `C:\` (but no drive letters) |
| `/home` | Personal directories for each user | `C:\Users\`, `/Users/` |
| `/root` | Home directory for the superuser, kept separate for security | No direct equivalent |
| `/etc` | System-wide configuration files | Windows Registry / `System32` |
| `/bin`, `/usr/bin` | Essential user-facing programs (`ls`, `cp`, `bash`) | `C:\Windows\System32\` |
| `/sbin`, `/usr/sbin` | System administration programs for root | `C:\Windows\System32\` |
| `/lib`, `/usr/lib` | Shared libraries for `/bin` and `/sbin` | `.dll` files |
| `/var` | Variable data — logs, print queues, mail spools | Spread across `C:\Windows\`, `ProgramData\` |
| `/tmp` | Temporary files, not guaranteed to survive reboot | `C:\Windows\Temp\` |
| `/dev` | Device files — hardware represented as files | No user-visible equivalent |
| `/proc` | Virtual filesystem exposing live process/kernel info | No direct equivalent |
| `/sys` | Virtual filesystem for kernel/hardware structure | No direct equivalent |
| `/boot` | Files needed to start the system, including the kernel | Windows Boot Manager (not user-navigable) |
| `/run` | Runtime data since the last boot (PIDs, lock files) | No direct equivalent |

### Removable Media

Continuing the "everything is a directory" principle, USB drives and optical discs are accessed through the filesystem tree, not separate drive letters. Modern systems typically auto-mount these under `/run/media/yourusername/disklabel` (older distros may use `/media`).

**Example:** If your username is `student` and you plug in a USB drive labeled `FEDORA`, it becomes accessible at `/run/media/student/FEDORA/`. A file called `README.txt` on that drive lives at `/run/media/student/FEDORA/README.txt` — directly analogous to Windows assigning that drive `E:\` and finding the file at `E:\README.txt`. Same concept, different addressing method.

> **Note:** The FHS is a **"trailing standard"** — it documents established practice rather than mandating it in advance. Distributions occasionally deviate slightly, and the standard evolves over time, but the directories above are consistent across the vast majority of systems you'll use.

## 4. A Closer Look at the Filesystem Hierarchy

### Case Sensitivity

One of the first differences you'll notice: Linux treats uppercase and lowercase letters in file and directory names as **completely distinct**. `/boot`, `/Boot`, and `/BOOT` are three entirely separate directories as far as Linux is concerned.

This is a real adjustment coming from Windows or macOS — both are **case-preserving** (they remember your capitalization) but **case-insensitive** (they don't distinguish between variations when looking things up), so `Documents`, `documents`, and `DOCUMENTS` all mean the same folder. Linux is fully **case-sensitive**: capitalization always matters.

**Example:** Typing `cd /Home` when the correct path is `/home` produces an error — it will not silently redirect you to the right place.

**Convention:** Stick to lowercase letters for files and directories you create yourself. This is the strong convention across the Linux ecosystem and avoids a whole category of hard-to-spot errors.

### The /usr Directory: Separating System from Software

You'll notice several root-level directories — `/bin`, `/lib`, `/sbin` — have counterparts under `/usr` (`/usr/bin`, `/usr/lib`, `/usr/sbin`). Here's why:

- Directories directly under `/` contain only what's strictly necessary to **boot the system and perform basic recovery** — the minimum needed before anything else loads. Think of these as the tools a technician would need to repair the system from scratch.
- Everything else — the broader collection of programs, libraries, and resources for a fully functioning system — lives under **`/usr`** (originally "Unix System Resources"), the operating system's general-purpose software layer.

| Directory | Contains |
|---|---|
| `/usr/bin` | The vast majority of user-facing commands and programs |
| `/usr/sbin` | System administration tools not required at boot |
| `/usr/lib` | Shared libraries for programs in `/usr/bin` and `/usr/sbin` |
| `/usr/share` | Architecture-independent data — documentation, icons |
| `/usr/local` | Software installed manually by the sysadmin, outside the package manager |

**Modern simplification:** On most current distributions, the `/bin` vs `/usr/bin` distinction has been removed entirely — `/bin` is simply a symbolic link to `/usr/bin`. This reflects that the original reason for the split (fitting the system onto multiple small disks) no longer applies to modern hardware. You'll still see both paths in documentation and scripts, but they lead to the same place.

**Key takeaway:** Looking for a program? Check **`/usr/bin`** first. Installed something manually or compiled from source? Check **`/usr/local/bin`**.

## 5. Viewing the Filesystem Hierarchy from the Graphical Interface

You don't need the command line to explore the filesystem — every major Linux desktop environment ships with a graphical file manager, and the experience is nearly identical across distributions.

### Getting There

- Open **Applications → Favorites → Files**, or
- Click **Activities**, where Files also appears if it's in your favorites

This opens your `/home/<username>` directory by default.

### Navigating Elsewhere

Use **Other Locations → Computer** to browse the rest of the filesystem — for example, navigating to `/usr/local/bin` to see installed scripts and binaries.
