## 1. The Linux Kernel

Once the boot loader pulls the kernel and the initial RAM-based filesystem (**initramfs**) into memory, the kernel officially takes control of the system. As the heart of the operating system, its first priority is transforming raw hardware components into a coordinated, usable system.

![Bootloader Loads Kernel and Initramfs into Memory](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/kernel-to-memory.png?raw=true)

As soon as the kernel is active in RAM, it begins a comprehensive configuration process to "claim" the hardware, driven by internal kernel functions like `start_kernel()` and a sequence of initcalls:

| Task | What Happens |
|---|---|
| **Memory Management** | Maps out physical RAM, deciding how to share it between the OS and the applications you'll run |
| **Processor Setup** | Identifies and initializes all available CPUs, preparing the system to handle multiple tasks simultaneously |
| **I/O and Storage** | Finds and configures all input/output subsystems and storage devices, from your keyboard to your hard drive |

**Example:** On a laptop with 4 CPU cores, this is the exact moment the kernel discovers all 4 cores exist and prepares to schedule work across each of them — before this step, the system doesn't even know how much processing power it has to work with.

### From Hardware to Early Userspace

The kernel does more than manage hardware — it also starts **user space**, the environment where your programs actually run. It uses the drivers and files stored in initramfs to create what's known as **"early userspace."**

This early userspace is critical: it contains the logic needed to find, check, and mount the primary root filesystem on your disk. Once that filesystem is verified and ready, the kernel transitions from this temporary environment to the permanent operating system, and finally loads the essential applications needed to finish the boot sequence.

## 2. /sbin/init and Services

Once the kernel finishes hardware setup and mounts the root filesystem, it launches a critical program: **`/sbin/init`**.

> **Note:** On systemd-based distros (covered below), `/sbin/init` is typically a symlink to the systemd binary — e.g., `/lib/systemd/systemd` or `/usr/lib/systemd/systemd`.

`/sbin/init` is the **first process** to run on the system and serves as the **"parent" of all other processes**.

![Kernel Launching the Init Process](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/kernel-launches-init.png?raw=true)

### The Role of the Init Process

| Responsibility | What It Means |
|---|---|
| **Process Initiation** | Starts the background services and applications required for the system to function |
| **System Management** | Nearly every process on your system traces back to init — the only exceptions are kernel processes the kernel starts directly |
| **Ongoing Maintenance** | Acts as manager for all non-kernel processes: cleans up after them when they finish, restarts login services as users log in and out |
| **System Shutdown** | Ensures all services stop correctly and data is saved before the system powers down |

**Example:** If you run `ps -ef` on any Linux system, you'll see PID 1 (init/systemd) sitting at the top of the process tree — trace any running process's parent chain back far enough, and it always leads there.

## 3. Linux Startup Alternatives: Why the Industry Evolved

### From SysVinit to Modern Standards

Historically, Linux used **SysVinit** (System V init) — a convention based on 1980s UNIX systems.

- **Sequential Loading** — SysVinit started services one by one, in a specific order.
- **Runlevels** — the system moved through different "runlevels," collections of scripts that started or stopped specific services depending on the system mode (single-user mode, multi-user graphical mode, etc.).

While this was the standard for decades, it was slow and rigid.

### The Limitations of the Old Way

**Sequential Bottlenecks** — SysVinit treated startup as a serial process: each task had to finish completely before the next could start. This prevented the system from using parallel processing on modern multi-core CPUs.

**The Need for Speed** — in the past, reboots were rare and startup time wasn't a priority. Today, mobile devices, embedded systems, and containers all require near-instant startup to be effective.

**Complex Maintenance** — older startup relied on complex shell scripts that were difficult to standardize across different hardware and distributions.

### The Path to systemd

Two major alternatives emerged to replace the aging sequential model:

| System | Origin | Outcome |
|---|---|---|
| **Upstart** | Developed by Ubuntu in 2006; later adopted by Fedora and RHEL 6 | Improved on SysVinit, but has since been phased out |
| **systemd** | First adopted by Fedora in 2011 | Became the standard for RHEL 7, SUSE, and Ubuntu |

Today, **systemd adoption is near-universal** across mainstream desktop and server distributions. Only deliberate exceptions remain — anti-systemd forks or lightweight/embedded distributions like Alpine.

**Example — why this matters for you as a beginner:** Because systemd is almost universal, the exact `systemctl` commands you learn on Ubuntu will work nearly identically on Fedora, RHEL, or SUSE. Learn it once, use it almost everywhere.

## 4. systemd Features

In modern Linux distributions, **systemd** serves as the system and service manager, replacing the older SysVinit process and streamlining how your computer boots and manages background tasks.

![SysVinit vs systemd](https://github.com/shaktikadam1630/DevOps_Notes/blob/main/Linux/images/sysvinit-vs-systemd.png?raw=true)

### Core Advantages

**Parallelization**
Unlike older methods that started services one by one (serialized), systemd uses aggressive parallelization — multiple services launch simultaneously, significantly reducing total boot time.

**Declarative Configuration**
systemd replaces complex, error-prone shell scripts with simple `.service` configuration files. These explicitly define dependencies (what must start first), execution commands, and success criteria.

**The New init**
On a systemd-enabled machine, the traditional `/sbin/init` is actually a symbolic link to `/lib/systemd/systemd`. This means systemd is the very first process to start (**PID 1**) and manages all others.

### Managing Services with systemctl

The `systemctl` command is your primary tool for interacting with systemd. Below, `apache2` is used as an example (common on Debian/Ubuntu; on Red Hat/Fedora it's usually `httpd`).

> **Note:** You can usually omit the `.service` extension — systemd assumes you mean a service unit.

**1. Real-Time Service Control** — change the state of a currently running service:
```bash
sudo systemctl start apache2
sudo systemctl stop apache2
sudo systemctl restart apache2
```

**2. Boot-Time Configuration** — control whether a service launches automatically at boot:
```bash
sudo systemctl enable apache2
sudo systemctl disable apache2
```

**3. Monitoring Service Health** — check if a service is running, view recent logs, or see its process ID:
```bash
sudo systemctl status apache2
```

**Example:** After installing a web server, running `sudo systemctl enable apache2` makes sure it automatically restarts every time the machine reboots — without this, you'd have to manually start it after every restart, which is easy to forget on a production server.

## The Full Picture

Once the kernel takes over from the boot loader, it spends its first moments claiming the hardware — memory, CPUs, storage — before launching `/sbin/init` as the very first user-space process and parent of everything that follows. For decades that meant **SysVinit**, starting services one at a time through rigid runlevels. Today, that job belongs to **systemd**, which starts services in parallel based on declared dependencies instead of a fixed sequence — and gives you one consistent tool, `systemctl`, to start, stop, enable, and monitor services across virtually any modern distribution you'll ever touch.
